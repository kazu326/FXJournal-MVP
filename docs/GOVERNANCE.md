## 1. 目的と適用範囲

### 1.1 本ドキュメントが担保すること

本ドキュメントは、FXJournal-MVP に関わる4者（ユーザー・FX業者・サロン運営者・アプリ導入クライアント）の利益が、**「教育」を核として整合し続けること**を担保する。具体的には次の3点を宣言し、その遵守を検証可能にする。

1. アプリがユーザーに対して行うすべての介入は、**ユーザーの退場兆候**のみをトリガーとすること（第4節）
2. アプリが最適化する指標は、**ユーザーの生存と規律**に関するものに限定すること（第3節）
3. 売上系の計測（LTV・MRR・解約率）は経営判断に閉じ、**ユーザー個別への働きかけの根拠にしないこと**（第5節）

### 1.2 想定読者

| 読者 | 本ドキュメントの用途 |
|---|---|
| 開発者・コントリビューター | 機能追加・指標追加・介入ロジック変更時の判断基準。PR レビューの根拠 |
| アプリ導入クライアント（サロン運営者） | 導入時に同意すべき利用境界（第6節）。自組織の運用が「教育核」から逸脱していないかのセルフチェック |
| 規制当局・外部監査者 | プリンシプルベース規制下での自己管理支援ツールとしての設計原則と、その検証手段（第8節・付録） |
| ユーザー（サロン会員） | 自分のデータがどう使われ、どう使われないかの確認。介入記録の開示請求権（第6節） |

### 1.3 位置づけと関連文書

- **README.md** — プロジェクトの背景と設計意図。本ドキュメントは README の「退場しないためのトレード支援」という意図を運用可能な制約に落としたもの

### 1.4 用語定義

| 用語 | 定義 |
|---|---|
| **退場** | 破産・資金枯渇・強制的な市場離脱、またはそれに直結する行動悪化（過剰取引、ルール違反の連発、損失後のリベンジトレード）。本アプリが防ぐ対象 |
| **解約** | サロンのサブスクリプション契約の終了。**退場ではない**。学習を完了し自走できるようになった会員の解約は、教育の成功である |
| **介入** | アプリまたは運営者が特定ユーザーに対して行う個別の働きかけ（DM・電話・コンテンツ推奨・制限変更等） |
| **教育的介入** | ユーザーの退場兆候をトリガーとし、ユーザーの生存・規律・学習を目的とする介入 |
| **売上防衛施策** | 解約防止・継続率向上を目的とする働きかけ（割引提供・リテンションメール等）。介入とは区別して管理する |
| **安全キュー** | 教師向けの退場兆候検知キュー（`v_risk_queue`）。系統 A（第4節） |
| **施策管理** | プラットフォーム管理者向けの介入実行画面（`interventions` テーブル群）。系統 B（第4節） |

本ドキュメントにおいて「**しなければならない／してはならない**」は必須要件（違反はガバナンス違反）、「**すべきである**」は推奨要件を意味する。

### 1.5 現行の運用文脈（参照運用）

本アプリのファーストクライアントは、CAMPFIRE + Discord で運営されるサロン「Effort」である（月額 ¥12,800・入会金 ¥20,000、毎週火曜 Zoom 講義＋ニュースレター）。同サロンは**退会自由・8日以内返金・休会制度・¥0 復帰可能**というユーザーファーストの設計を採っており、「解約を防ぐことを目的にしない」という本ドキュメントの原則は、この運用実態と整合している。

本ドキュメントの役割は、この整合が**運営者の善意に依存している現状**を、コード・スキーマ・契約による**構造的な保証**に置き換えることである。2026-07-03 の監査では、ユーザー向けレイヤーは設計意図に忠実である一方、管理者レイヤーには意図と逆行する構造が3点確認された（第4節・第5節・第7節に詳述）。

## 2. 4者の利益相反マップ

### 2.1 4者の利益と最適化目標

| 主体 | 利益 | 最適化目標 | 本アプリに求めるもの |
|---|---|---|---|
| **1. ユーザー（サロン会員）** | 破産せず市場に継続参入する（退場防止） | 生存期間の延長・ルール遵守率の向上・見送り判断の質の向上 | 衝動を抑える仕組み、規律の可視化、負けても続けられる記録 |
| **2. FX業者** | ユーザーに取引を続けさせる（手数料収益） | 取引頻度の増加・ポジションサイズの拡大 | （本アプリとの直接関係なし。ただしユーザー行動を経由して利害が及ぶ） |
| **3. サロン運営者** | 会員にサブスクを維持させる（売上維持） | 解約率の低下・MRR の増加 | 会員の状態把握、コーチング補助、経営指標 |
| **4. アプリ導入クライアント（=サロン運営者）** | アプリを「教育の核」として使うか、別の目的で使うかで全く別物になる | 教育核なら 1 と一致。教育不在なら 3 の売上防衛に純化 | 本ドキュメントが拘束する対象 |

### 2.2 主要な相反対

#### 相反 C-A：ユーザーの生存 vs 業者の取引量

取引を増やすことは、そのままユーザーの退場リスクを高める。FX業者の最適化目標（頻度・サイズ）とユーザーの最適化目標（生存・規律）は**構造的に逆向き**である。

- 本アプリの対応：取引回数に日次上限を設け（デフォルト2回）、見送り（skip）は無制限かつ取引記録より高い XP（+4 > +3）を付与する。取引頻度を増やす方向の演出・報酬・通知は**実装してはならない**（第3節ブラックリスト B-1）
- 監査確認：手数料・スプレッド・業者収益・アフィリエイトに関するコード/データはコードベースに概念ごと不存在。この不存在状態を**維持しなければならない**

#### 相反 C-B：ユーザーの退場防止 vs サロンの MRR

**解約が「正しい判断」になり得る**。学習を完了して自走できるようになった会員、経済状況が変わった会員、取引そのものをやめる決断をした会員にとって、解約は教育の成功または合理的選択である。このとき解約を防ぐ働きかけは、ユーザーに対する害となる。

- 本アプリの対応：解約防止をユーザー個別介入の目的に**してはならない**。解約率・MRR は経営指標として集計はできるが、個別ユーザーへの働きかけの選定基準に使うことを禁止する（第3節 N 分類、第5節）
- 監査確認：現状の施策管理画面はこの原則に違反している（`getRiskLevel` の第一条件が `subscription_status !== 'active'`、`discount_offer` の期待成果が「解約防止」）。第7節の是正対象

#### 相反 C-C：教育的介入 vs 売上防衛施策

現状、同一の `interventions` テーブルで両方が実行可能である。これは単なる実装の粗さではなく、**教育介入の実績データと売上防衛の実績データが混ざり、「介入の成功率」が何の成功を意味するのか判別不能になる**という計測汚染を引き起こす。さらに、教育目的で収集された行動データ（Gate 遵守率・見送り率・感情スコア）が、解約防止ターゲティングに転用可能な状態に置かれる。

- 本アプリの対応：介入と施策をテーブル・画面・効果測定のすべてで分離**しなければならない**（第4節・第7節）

### 2.3 整合条件：「教育が核」の操作的定義

「教育が核である」とは、次の3条件がすべて成立している状態を指す。1つでも欠ければ、本アプリは変質しているとみなす。

1. **介入トリガー条件** — ユーザー個別への介入は、退場兆候（第3節ホワイトリスト由来のシグナル）のみをトリガーとする
2. **最適化指標条件** — プロダクト改善・演出・報酬設計が最適化する指標は、第3節ホワイトリストに限定される
3. **売上指標隔離条件** — LTV・MRR・解約率は集計・閲覧できるが、ユーザー個別の画面・介入選定・優先度付けに接続されない

## 3. 指標の分類

すべての指標は次の3分類のいずれかに属する。新しい指標を導入する PR は、**どの分類に属するかを PR 説明に明記しなければならない**（分類の変更は第9節の改訂手続きに従う）。

### 3.1 最適化してよい指標（ホワイトリスト）

プロダクトが改善・演出・報酬・介入トリガーに使ってよい指標。

| ID | 指標 | 定義・現行実装 |
|---|---|---|
| W-1 | **退場率** | 破産・長期離脱に至ったユーザーの割合。最重要 KPI であり、これの最小化がプロジェクトの存在理由 |
| W-2 | **ルール遵守率** | RR ≥ 2.7・リスク ≤ 2%・日次上限の遵守。`trade_logs` の `gate_*_ok`・`post_gate_kept` |
| W-3 | **見送り率と見送り理由の質** | skip 記録の頻度と内容。見送りは失敗ではなく成果として扱う（XP +4、履歴での賞賛表示） |
| W-4 | **学習完了率・理解度自己申告** | 講義・スライドの完了（`learning_progress`）。XP 最大配分（+10）の対象 |
| W-5 | **記録継続日数** | ログインストリーク・記録の継続。勝敗と無関係に「記録する行為」自体を強化する |
| W-6 | **Gate 通過率** | 事前チェック 4 項目の成立率。通過率が低いユーザーは介入（教育的サポート）の対象候補 |

### 3.2 最適化してはならない指標（ブラックリスト）

これらの指標を増加（または減少）させる方向の機能・演出・介入を実装してはならない。計測自体が禁止されるわけではないが、**最適化目標に据えた時点でガバナンス違反**となる。

| ID | 指標 | 禁止理由 |
|---|---|---|
| B-1 | **取引回数の増加** | FX業者の利益に直結し、ユーザーの退場リスクを直接高める（相反 C-A） |
| B-2 | **MRR・解約率をユーザー個別介入の根拠にすること** | 解約が正しい判断である場合に害となる（相反 C-B）。経営集計としての閲覧は N 分類で許容 |
| B-3 | **ポジションサイズの拡大** | リスク 2% 制約の実質的な骨抜きにつながる |
| B-4 | **アプリエンゲージメント時間の延長** | 滞在時間・セッション数それ自体を伸ばす設計はダークパターン化の入口。本アプリの記録動線は「取引前 30 秒・取引後 60 秒・見送り 15 秒」であり、**短いことが正しい** |

### 3.3 計測は可能だが、介入トリガーに使ってはならない指標

| ID | 指標 | 扱い |
|---|---|---|
| N-1 | **サブスク継続月数・LTV**（`v_user_ltv`） | サロン経営指標として集計・閲覧可。ユーザー個別の行動介入の根拠に使うことを**禁止**（第5節） |
| N-2 | **MRR・ARR**（`v_mrr_arr_summary`） | 同上。経営ダッシュボードに閉じる |
| N-3 | **解約率・解約理由**（`v_churn_analysis`） | 同上。解約理由の集計はプロダクト改善（教育コンテンツの欠陥発見）に使ってよいが、個人を特定した引き留めに使ってはならない |

## 4. 介入システムの目的境界

本アプリには性格が正反対の2系統の介入システムが存在する。2026-07-03 監査で確認された実態と、それぞれの境界を以下に定める。

### 4.1 系統A：安全キュー（教師向け）— 維持・拡張してよい

- **実体**：`v_risk_queue`（`supabase/sql/risk_queue_v2.sql`）と教師ポータルのキュー UI（「安全確認DM」）
- **トリガー（すべて取引行動のみ）**：
  - 週内ルール違反 2 件以上（`alert_invalid`）
  - 見送りゼロで取引あり（`alert_skip0`）
  - 週上限超過（`alert_over_weekly`）
- **目的**：ユーザーの退場防止。サブスク・売上情報を一切参照しない
- **判定**：✅ 教育核に整合。この系統は維持し、拡張してよい

**拡張条件**：新しいトリガーを追加する場合、そのトリガーは第3節ホワイトリスト（W-1〜W-6）由来のシグナルでなければならない。「取引の減少」「ログイン減少」等をトリガーに追加する場合は、それが退場兆候（記録の途絶＝離脱前兆）としての追加なのか、エンゲージメント維持（B-4）目的なのかを PR で明示し、後者は却下される。

### 4.2 系統B：施策管理（プラットフォーム管理者向け）— 分離を要する

- **実体**：`interventions` / `intervention_outcomes` / `measurement_schedule` テーブル群と `/admin/interventions` 画面
- **監査で確認された現状（2026-07-03 時点）**：
  - 対象選定ロジック `getRiskLevel` の**第一条件が `subscription_status !== 'active'`** であり、取引行動が一切含まれない（`src/pages/admin/InterventionManagementPage.tsx`）
  - `intervention_type` に `retention_email`・`discount_offer` を含む（`supabase/migrations/20260212210000_intervention_management.sql`）
  - `discount_offer` のテンプレートは「継続割引を提供してリテンションを促進します。」、期待成果は **「解約防止」**（`src/components/admin/InterventionModal.tsx`）
  - `trigger_reason` は自由テキストで CHECK 制約なし。実際に記録される値は「管理者による手動選択」「個別対応」
- **判定**：❌ 現状は売上防衛に構造上開放されており、教育核と逆行する

### 4.3 分離の原則（宣言）

本ドキュメントは以下を原則として宣言する。**実装は本ドキュメントの対象外であり、別途マイグレーションおよびフロントエンド改修として行う**（要件の詳細は第7節）。

| ID | 原則 |
|---|---|
| D-1 | `interventions` テーブルは**教育的介入専用**とする。売上防衛施策（割引・リテンションメール等）を教育介入と同一テーブルで管理してはならない。業務上必要なら別テーブル（例：`marketing_actions`）に分離する |
| D-2 | 教育的介入のトリガーは、退場兆候の**閉じた語彙**（ENUM）に制限する。自由テキストの `trigger_reason` を介入の一次根拠にしてはならない |
| D-3 | 介入の効果測定（`intervention_outcomes.metric_name`）は第3節ホワイトリスト指標に限定する。「解約防止率」を教育介入の成功率に合算してはならない |
| D-4 | 介入対象の選定画面は、売上系ビュー（`v_user_ltv`・`v_mrr_arr_summary`・`v_churn_analysis`）を参照してはならない。行動変容データと売上データを同一ビューに融合している `v_behavior_compliance_report` / `v_compliance_report_with_interventions` は、売上列を除去するか教育列のみの派生ビューに置き換える |

## 5. v_user_ltv の定義と制約

### 5.1 現行実装の事実

`v_user_ltv`（`supabase/migrations/20260212213500_compliance_extensions.sql`）は次のように実装されている。

```sql
COALESCE(SUM(p.amount), 0) AS lifetime_value
-- ...
LEFT JOIN subscriptions s ON u.id = s.user_id
LEFT JOIN payments p ON s.id = p.subscription_id AND p.status = 'completed'
```

すなわち現在の LTV は**「サロンのサブスクリプション売上の累計」**である。FX業者の手数料はコードベースに概念ごと存在せず、教育的価値（学習完了・行動改善・生存期間）の集計も含まれていない。純粋にサロン運営者の SaaS 経営指標である。

### 5.2 宣言

| ID | 宣言 |
|---|---|
| L-1 | この LTV は**サロン運営者の経営指標**であり、ユーザーの利益を測る指標ではない。名称が与える印象（顧客生涯「価値」）と実体（支払累計）を混同してはならない |
| L-2 | ユーザー個別の行動介入のトリガー・対象選定・優先度付けに `v_user_ltv` を使用することを**禁止**する（N-1） |
| L-3 | `v_user_ltv` および `users.lifetime_value` キャッシュ列は、経営ダッシュボード以外の画面（介入管理・会員一覧・教師ポータル）に表示してはならない |

### 5.3 将来の「教育的 LTV」

プロジェクトオーナーの定義は「**ユーザーの教育的利益と継続のための LTV であり、FX業者の LTV ではない**」である。この定義に沿った指標（仮称：`v_user_educational_value`。構成要素の候補：生存期間・学習完了・ルール遵守率の改善デルタ・見送り判断の質）を将来定義する場合は、**本ドキュメントの改訂として**その定義・許容される用途・禁止される用途を第5節に追記する。定義なきまま「教育的 LTV」の名で売上指標を再ラベルすることを禁止する。

## 6. クライアント（アプリ導入サロン運営者）への保証要件

本アプリ（特に OSS 化される行動介入エンジン）を導入するサロン運営者は、以下の要件に同意しなければならない。要件は `docs/CLIENT_TERMS.md`（利用規約テンプレート・別途作成）として契約条項化される。

本節の内容は、`docs/CLIENT_TERMS.md` においてクライアント向け利用条件として契約文書化される。

### 6.1 要件

| ID | 要件 |
|---|---|
| C-1 | 介入機能は**ユーザーの退場兆候対応に限定**して使用すること。サロン解約兆候・取引減少・エンゲージメント低下を介入のトリガーにしてはならない |
| C-2 | LTV / MRR 系ビュー（`v_user_ltv`・`v_mrr_arr_summary`・`v_churn_analysis` およびその派生）を、ユーザー個別介入の選定基準に用いないこと |
| C-3 | 売上系施策（割引提供・リテンションメール等）を教育的介入と同一テーブル・同一画面で管理しないこと（D-1 の運用面） |
| C-4 | `interventions` テーブルの監査ログ（誰が・いつ・誰に・何をトリガーとして・何を実施したか）を保持し、**ユーザー本人からの開示請求に応じること** |
| C-5 | 本ガバナンス文書および第8節の監査ポイントに基づく監査（自動検証クエリの実行結果提出を含む）に協力すること |

### 6.2 違反時の措置

上記要件への違反が確認された場合、プロジェクトは当該クライアントに対する**利用許可を終了する**。具体的には以下の二層で構成する。

- **クライアント契約の層**：`docs/CLIENT_TERMS.md` に基づく契約解除。公式サポート・アップデート提供・名称/ブランドの使用許諾・ホスティング支援の終了
- **OSS ライセンスの層**：コード自体の OSS ライセンスは別途選定する（2026-07-03 時点で LICENSE ファイルは未選定・`package.json` は `private: true`）。一般的な OSS ライセンスは利用目的による差別を許容しないため、**「教育核」の強制はコードライセンスではなくクライアント契約・商標・監査可能性の三点で担保する**。ライセンス選定時は本節との整合を確認すること（第9節）

### 6.3 ユーザーの開示請求権

ユーザー（サロン会員）は、自分を対象として実行された介入の記録（実施日時・種別・トリガー・実施内容）の開示を、クライアントまたはプロジェクトに請求できる。第7節のトリガー ENUM 化により、開示された記録が「退場兆候由来か否か」を機械的に検証できる状態を維持する。

## 8. 監査可能性

### 8.1 監査ポイント

| ID | 監査ポイント | 合格基準 | 検証手段 |
|---|---|---|---|
| A-1 | 売上系施策が教育介入テーブルに混入していないか | `interventions` に `retention_email` / `discount_offer` 型のレコードが 0 件 | 付録A クエリ 1 |
| A-2 | 介入トリガーが退場兆候の語彙に収まっているか | ENUM 制約が存在し（T-1 実装後）、既存レコードが全件語彙内 | 付録A クエリ 2 |
| A-3 | 介入の効果測定が教育指標のみか | `intervention_outcomes.metric_name` が第3節ホワイトリスト由来の語彙のみ | 付録A クエリ 3 |
| A-4 | ビューの権限設定 | public スキーマの全ビューに `security_invoker=true` | 付録A クエリ 4 |
| A-5 | `v_user_ltv` がユーザー個別介入画面で参照されていないか | 介入系フロントエンドコードに LTV 系ビュー/列への参照が 0 件 | 付録B 検査 1 |
| A-6 | 介入記録の説明可能性 | 全介入レコードにトリガー時点のメトリクススナップショット（`trigger_metric`）が付与されている | 付録A クエリ 5 |

### 8.2 実施主体と頻度

- **CI（毎 PR / 毎リリース）**：付録B の静的検査、および（マイグレーション適用環境では）付録A のスキーマ系クエリ（A-2 の制約存在確認・A-4）
- **定期監査（四半期）**：プロジェクトオーナーまたは指名された監査担当が付録A 全クエリを本番データベースに対して実行し、結果を記録する
- **クライアント監査（導入時および年次）**：クライアントは自環境での付録A 実行結果をプロジェクトに提出する（C-5）

## 9. 改訂手続き

### 9.1 改訂の種類と要求事項

| 制約の**追加**・強化 | 改訂 PR に動機と影響範囲を記載。メンテナ承認 |

| **ライセンス条項・クライアント保証要件（第6節）の変更** | 別途文書化（変更内容・理由・発効日）し、**既存クライアント全員に通知**すること。通知から発効まで合理的な猶予期間を置く |

### 9.2 改訂 PR の必須記載事項

1. 改訂の種類（上表のいずれか）
2. 変更前後の対比
3. 理由（緩和の場合は「この制約が守ろうとしたものが、なぜもう守る必要がないのか、または別の手段でどう守るのか」）
4. 検討した代替案

## 付録A：自動検証 SQL

> 実行対象：Supabase（PostgreSQL）。T-1・T-2 実装前でも実行できるよう、現行スキーマ（TEXT 列）を前提に記述している。ENUM 移行後はクエリ 2 の暫定版は不要になる。

```sql
-- クエリ 1（A-1）：売上系施策の混入検査 —— 結果は 0 件であるべき
SELECT id, user_id, intervention_type, trigger_reason, executed_at, executed_by
FROM interventions
WHERE intervention_type IN ('retention_email', 'discount_offer');

-- クエリ 2（A-2）：トリガー語彙検査（ENUM 移行前の暫定版）—— 結果は 0 件であるべき
SELECT trigger_reason, COUNT(*) AS cnt
FROM interventions
WHERE trigger_reason NOT IN (
  'overtrading',         -- 週上限超過
  'rule_violation',      -- ルール違反連発
  'no_skip_discipline',  -- 見送りゼロ
  'learning_stall',      -- 学習停滞
  'record_inactivity'    -- 記録途絶（離脱前兆）
)
GROUP BY trigger_reason
ORDER BY cnt DESC;

-- クエリ 2'（A-2）：ENUM 制約の存在確認（T-1 実装後）—— 結果は 1 件であるべき
SELECT t.typname
FROM pg_type t
WHERE t.typname = 'intervention_trigger_type' AND t.typtype = 'e';

-- クエリ 3（A-3）：効果測定指標の語彙検査 —— 結果は 0 件であるべき
SELECT metric_name, COUNT(*) AS cnt
FROM intervention_outcomes
WHERE metric_name NOT IN (
  'rule_ok_rate',              -- W-2
  'skip_rate',                 -- W-3
  'learning_completion_rate',  -- W-4
  'record_streak_days',        -- W-5
  'gate_pass_rate',            -- W-6
  'survival_days'              -- W-1
)
GROUP BY metric_name
ORDER BY cnt DESC;

-- クエリ 4（A-4）：security_invoker 未設定ビューの検出 —— 結果は 0 件であるべき
SELECT c.relname AS view_name
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'v'
  AND n.nspname = 'public'
  AND (c.reloptions IS NULL
       OR NOT ('security_invoker=true' = ANY (c.reloptions)));

-- クエリ 5（A-6）：スナップショットなし介入の検出 —— 結果は 0 件であるべき
SELECT id, user_id, intervention_type, executed_at
FROM interventions
WHERE trigger_metric IS NULL;
```
